# Kit lifecycle boundary

This integration is primarily a **consumer** of an established kit. An explicit request to establish, refresh or export the kit is different from using it to build a page.

First look for the existing Client Experience framework's authoring contract and workflow (for example `/.ai/client-experience/contract.md`, its existing `workflows.md`, and its `client-experience` skill). Read the actual files and use their establish/refresh/export mode in the same session. Do not launch another agent or recurse through the production route. The prior framework's canonical schema and permission checks remain in force.

Where a repository only contains the kit and this integration, do not pretend the full authoring framework or export tools are installed. For an explicit small correction, preserve the existing schema, scope and evidence; record the correction and validate with actual available tools. For a full establishment/export request requiring missing contracts, disclose what is missing, use supplied canonical authoring instructions if available, and deliver the supported portion without inventing schema fields or approvals. This profile is not a replacement full brand-extraction product.

A kit change updates its proper owning files and registered assets/captures, then any requested derived exports. It does not automatically update every existing prototype. Keep the current one-brand `/brand-kit/` location. Never copy task-specific preferences into brand rules merely because a generated image was attractive. Do not bypass unknown asset permissions or fabricate hashes to satisfy a validator.

Existing `client-experience` authoring skills may coexist with this `brand-experience` production skill. For ordinary user-facing work the root production route governs. Reconcile overlapping legacy descriptions when deliberately maintaining the framework; the integration installer never deletes another skill or rewrites unrelated governance files.
