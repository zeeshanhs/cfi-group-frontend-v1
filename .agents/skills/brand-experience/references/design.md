# Design profile

Use for new visual directions, page layouts, screen specifications, information hierarchy, visible copy and adaptations into new contexts. Read the shared contract first. Do not render or implement in a specification-only task.

## Read and choose

Read the task/system specification and any current screen document. Establish the user outcome, content, primary flow, viewport, delivery medium and what is explicitly excluded. Apply relevant experience rules, DES/IMG rules, patterns and foundation roles. Inspect actual selected evidence and identity assets. A logo plus palette is not a design direction.

For a small change, reuse the existing direction and resolve only the affected decision. For a new page or flow, choose one coherent task-appropriate direction unless alternatives were requested. Specify the effect of the chosen rules: what leads, what supports, what creates confidence, what gets visual emphasis and why imagery is needed or not needed. Preserve brand expression without copying a marketing page into every application.

## Resolve the shared basis

Establish composition, hierarchy, alignment, whitespace/density, typography roles, color proportions, surface hierarchy and graphic/imagery treatment. Define navigation/shell, recurring components and action emphasis. For web products, include applicable interaction states, keyboard/focus behavior and responsive transformations. Use actual meaningful headings, action labels, terminology and enough coherent synthetic data to support the demo flow. Do not add unsupported business claims or product functionality.

Record the preserve/adapt/extend/exclude decisions and applicable rules in the existing task artifact. Exact reusable values belong in `theme.css`; layout-specific dimensions and new patterns belong in the task/application. Source absence is not permission to label an invented design as established.

## Multi-screen specifications

When the requested scope genuinely needs a coordinated screen document, use the existing one or `templates/screen-specifications.md`. Keep the established filename; default to `SCREEN_SPECIFICATIONS.md` only for a new artifact. Map every in-scope source requirement to a screen/state or explicitly state deferred, excluded, unresolved or unsupported. Do not silently drop a requirement to fit a shorter document.

Specify one shared design basis plus complete screen records. Give screens stable IDs and business-readable names. States such as expanded, empty or error are not automatically new screens. Each record resolves outcome, entry/exit, information order, content, layout, assets, interactions, responsive behavior, brand deviations, render brief and acceptance checks. A renderer must not invent consequential new design decisions.

Image and HTML/code outputs use the same screen + state + viewport + revision. Required imagery uses the imagery profile; actual implementation uses the web profile. An image is not a prerequisite for code, and a screenshot does not become the new source of functional requirements.

## Finish

Deliver the requested plan/specification as actual files when requested and possible. Identify the first useful screen for rendering and material assumptions. Verify cross-screen names/data, asset dispositions and requirement coverage. Do not claim client approval, screen rendering or browser inspection for a document-only output.
